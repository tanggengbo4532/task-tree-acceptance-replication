# 问题台账（阻断 / 非阻断追踪）

> 纪律：非阻断不等于不存在——登记留档，总报告如实列出；阻断问题未修不得标记节点通过。
> 误判的条目要正式「排除」并写明证据链，不能悄悄删。
> 状态机：`疑似 → 复核中 → 修复中 → 待回归 → 已关闭 / 已排除`
> 每个节点完成后更新一次；记录者写节点总结时与本台账逐条对账。

## 条目展开（重要条目单独写）

### B1 <标题>

- **所属节点**：（任务树编号）
- **现象**：（测试原话 + 坐标/界面/操作序列）
- **分级**：阻断（完不成节点任务：流程走不通/引导误导/崩溃/数据错误）／
  非阻断（视觉瑕疵/文案风格/体验建议）——写明判定依据
- **初判**：（开发第一眼的猜测——只是假设）
- **复核**：截图复查 / 按键回放 / headless 追踪 / 引擎日志 → 成立 / 不成立 / 部分成立
- **归因**：误操作 / 历史数据 / 基准行为 / 环境问题 / 真 bug（哪一层）
- **修复**：（改动文件 + 设计要点）
- **真机闭环**：同路径复现 → 站定观察 → 日志对账 → 回归结果
- **状态**：已关闭 / 已排除（排除要写「为什么当时会出现」的完整解释）

## 经验法则

- 复核结论只有三种：成立 / 不成立（排除）/ 部分成立（改写描述）
- 「没复现」不等于「已排除」；排除必须有确定性解释或确定性用例
- 修复方案先问：这个状态还有哪些写入点？这个信号有哪些消费者？
- **同类问题第 2 次收到**：先做设计/架构审查，从设计层修复并写 `ARCH_REVIEW`；不要用临时豁免、调试开关或让测试绕过卡点来"关闭"问题。
- 测试提出的**建议**与 bug 分开记录：建议要给出采纳结论（采纳→怎么改；不采纳→为什么）。
