# 双进度人机协同（v3.3.3）

> 版本：**v3.3.3**｜状态：**人机协同模式（写死）**｜适用：Lead / 开发 / 测试 / 记录全员
> 关联：`references/testing/progress-first.md`、`references/standards/slot-safety.md`（**槽安全铁律 v3.3.3**）、`templates/anchor-ledger.md`、`references/standards/anchors-and-saves.md`、`references/standards/no-cheat.md`
> 一句话：**进度一=用户专用；进度二=团队专用；用户测过的节点团队直接记 PASS 不复测；团队跑过的进度交用户复测，用户确认后双进度对齐到通过点；下一轮从用户进度一继续。**

## 0. 总览：三个槽位角色

| 槽位 | 归属/用途 | 写入权 | 读取权 | 说明 |
|---|---|---|---|---|
| **进度一** | **用户专用**（用户测试 + 保存） | **仅用户** | 团队**只读载入** | 团队**绝不写进度一**（不保存/不覆盖/不清空）；用户进度是权威起点 |
| **进度二** | **团队专用**（团队测试/续测保存） | **仅团队** | 用户可只读载入复测 | 团队"当前续测点"；**可覆盖**（每次保存更新）；记录在案 |
| 其余测试槽（槽 3/4/5） | **固定锚点（可选）** | 团队（只读建锚点后不覆盖） | 只读 | 节点稳定起点；只读、不覆盖（见 `templates/anchor-ledger.md` §1） |

**核心分工**：用户负责"从用户视角测试并保存进度一"；团队负责"从进度一续做、验证、修复，把推进保存到进度二"；用户再回来复测团队进度，双方在"用户验收通过的进度"对齐。

## 1. 规则一：进度一用户专用、进度二团队专用

1. **进度一 = 用户专用**：用户测试并保存自己的进度；**团队不写进度一**（只读载入后另存到进度二）。
2. **进度二 = 团队专用**：团队测试/续测/修复验证时保存；**团队只写进度二**，覆盖更新即可。
3. **团队从进度一接续**：团队需要从用户进度继续时，**只读载入进度一** → 立刻把当前位置/状态**另存到进度二**（团队续测起点）→ 之后团队推进只写进度二。
4. 用户可**只读载入进度二**复测团队进度（不覆盖）；用户自己的保存仍写进度一。

**禁止（槽安全铁律 v3.3.3）**：
- ❌ 团队保存/覆盖/清空进度一（会破坏用户进度；**任何情况不写用户槽**）；
- ❌ 把团队进度写进进度一（哪怕"为了续测"）；
- ❌ 用户进度二与进度一混用/互相覆盖；
- ❌ **自动化在菜单/存档/对话框/战斗/过场界面盲按**（必须先截图/状态分类确认 UI=游戏世界）；
- ❌ 依赖默认槽位保存（禁止默认光标=进度一；必须显式槽位+归属校验）。

> 槽安全完整铁律（用户槽不可变/输入前置门禁/显式槽位归属/误覆盖=P0）见 `references/standards/slot-safety.md`。

## 2. 规则二：用户测过的节点 = 团队直接记录 PASS，不再复测

- **判定依据**：用户明确告知某节点已通过（+ 位置/证据/截图/原话），或用户进度一已推进到该节点之后；
- **团队动作**：在验收记录/任务树中**直接标 PASS（用户验收）**，**不再派测试复测该节点**；
- **团队从用户进度一接着往下做**：只读载入进度一 → 另存进度二 → 从该位置继续推进/验证；
- 仅 **用户新报该节点 bug** 或 **该节点代码变更** 时才重开（单次判定规则不变）；
- **反例**：用户已 PASS 的节点，团队又从头复测一遍 → 浪费、重复劳动；或团队不信任用户结论要求重测 → 违反本规则。

## 3. 规则三：团队跑过的进度 → 用户复测 → 双进度对齐

1. **团队进度出来**：团队在进度二上推进/修复后，需要用户回来复测；
2. **交接给用户**：写清「团队进度状态（进度二：场景/坐标/PASS 节点/待复测节点）」+ 复测方法（用户可只读载入进度二，或从进度一按引导走到该点）；
3. **用户复测并告知结果**：通过/不通过 + 证据；
4. **双进度对齐到用户验收通过的进度**：
   - **团队写进度二**：把进度二同步到用户验收通过的进度点（覆盖更新，记录）；
   - **进度一由用户保存**：由用户在通过点保存进度一（**团队不代写**；如用户明确要求团队协助，只记录不可代保存）；
   - 双方记录「进度一/进度二 = 同一通过点（场景/坐标/构建/时间）」；
5. **团队据此记录**：用户通过的节点记 PASS；用户新报问题按 bug 流程（先存进度二再报）处理。

**反例**：
- ❌ 团队跑完不交接、用户不知道从哪复测；
- ❌ 用户复测通过后进度一/二仍停在旧点（下一轮又从头）；
- ❌ 团队代写进度一"A 到通过点" → 违反规则一。

## 4. 规则四：下一轮继续（循环）

**下一轮开始**：
1. 读用户最新**进度一**（只读）作为权威起点；
2. 团队从进度一位置另存**进度二**（续测起点）；
3. 用户已 PASS 节点保持 PASS、不复测；
4. 团队继续推进/修复/验证（写进度二）→ 再交用户复测 → 对齐（规则三）；
5. 每轮如此循环，进度一只由用户写、进度二只由团队写。

## 5. 报告 / 交接字段（写死 5 项）

每份测试报告/交接/章节验收必须写清：

```text
【用户进度状态】<进度一：场景/楼层/坐标/中央提示/构建/时间；用户已保存/只读>
【团队进度状态】<进度二：场景/楼层/坐标/中央提示/构建/时间；团队最后保存点>
【用户已 PASS 节点】<用户确认通过的节点清单（团队直接记录 PASS，不复测）>
【团队待用户复测节点】<团队进度中等待用户复测的节点清单（含进度二位置）>
【下一步】<团队从进度一/二哪个点继续；或等用户复测/决定>
```

## 6. 反例合集

| 错误做法 | 后果 | 正确做法 |
|---|---|---|
| 团队保存/覆盖进度一 | 用户进度被破坏/丢失 | 团队只读进度一，另存进度二 |
| 用户已 PASS 节点团队又复测 | 重复劳动/交付慢 | 直接记录 PASS，不复测 |
| 团队进度不交接用户 | 用户不知道复测什么 | 写清团队进度状态+待复测节点 |
| 用户通过后不更新进度一/二 | 下轮从头再来 | 双进度对齐到通过点（用户存进度一/团队存进度二） |
| 团队代写进度一 | 违反用户专用 | 进度一由用户保存；团队只写进度二 |
| 进度二当用户进度 | 双进度混乱 | 明确两槽归属与写入权 |

## 7. 槽位保护与每轮检查清单

**槽位保护**：
- 进度一：用户专用，**团队只读**；
- 进度二：团队专用，用户可只读复测；
- 槽 3/4/5：固定锚点（只读、不覆盖）；
- 不占用/不覆盖用户槽；不把进度二登记成固定锚点。

**每轮检查**：
- 开轮：读用户进度一（只读）→另存进度二；核对用户 PASS 清单；确认待复测节点；
- 遇 bug：停手→保存进度二→记录→报 bug；
- 用户复测后：双进度对齐到通过点；更新 PASS/待复测清单；
- 交接：5 项字段齐全。

## 8. FAQ

**Q：团队能不能直接读进度一继续？** 能——只读载入，但续测必须另存进度二；团队不写进度一。
**Q：用户已 PASS 节点，团队还要写证据吗？** 记录用户确认（原话/位置/截图）即可，不重新跑。
**Q：用户复测通过后进度一谁保存？** 用户自己保存（团队可提示保存点，但不代写）；团队把进度二同步到同一点。
**Q：团队跑过的进度用户怎么复测？** 可只读载入进度二，或从进度一按引导走到团队通过点；报告里写清进度二位置。
**Q：进度二可以覆盖吗？** 可以——它是团队当前续测点；历史以报告/交接文字留档。

## 9. 与其他规则的关系

- **progress-first.md**：本文件是"双进度"细化；bug 先存进度（存进度二）、单次判定、锚点/进度区分仍适用；
- **no-cheat**：双进度来自真实操作/合法存档；团队不写用户进度、不伪造进度；禁传送/跳步/自动置 stage；
- **固定锚点**：可选，用于节点稳定起点（只读）；与双进度分开登记；
- **报告/交接**：5 项字段（§5）为最小口径，缺一不合格。
