# 通用案例研究（脱敏）

> 来源：某实际游戏项目（引擎：Godot；规模：多场景 + 剧情 + 战斗 + 存档）的多轮黑盒验收沉淀。
> 已脱敏：不出现项目名、公司名、角色名、文件路径细节；量化数字均为真实记录（来源见 `probes-and-metrics.md` §7 引用表与本项目 `tester-report.md` 对应章节）。
> 每个案例结构：背景 → 证据方法 → 结论（根因层面）→ 可复用规则。

## 案例 A：引导重复 / 矛盾 / 目标不推进

### A1 背景

用户反馈"客栈段引导混乱"。黑盒复现时发现同一屏幕同时存在多套引导：

1. **顶栏**：地点 + 目标（例："客栈二楼回廊：跟黄点到楼梯口，按住 DOWN 下楼"）；
2. **中央条**：下一步按键 + 剩余格（例："下一步【↑】（剩 48 格）"）；
3. **地面黄点/黄框**：路径可视化（另一套目的地的路径）；
4. **调试浮层**：正常启动（无调试参数）竟然显示"按：← / 距离 N 格（楼梯口）"，遮挡左 1/3 画面；
5. 楼梯口：顶栏"按住 DOWN 下楼"与中央"按住 UP 上楼"**同时出现且方向相反**；
6. 上楼后目标又指"下楼"，形成**上下楼循环**；
7. 后段还出现"引导指向某 NPC，但房间内该 NPC 未出现、空格无效"的空指引。

### A2 证据方法（全部黑盒可见）

- **引导元素清单法**：固定位置截完整帧，逐帧列出所有引导来源（顶栏/中央/地面标记/边缘箭头/浮层/已到达状态），判定"同一目标或按键信息出现 ≥2 处 = 重复"；
- **逐状态检查**：正常行走、到达交互点、交互中、对白中、场景切换前后，各截一帧核对（开发容易只修"行走"一种状态）；
- **目标文本序列**：记录"顶栏地点 + 中央目标文本"随位置变化，要求**单调推进**（不出现"下楼→上楼→下楼"）；
- **方向一致性**：同一帧内比较"中央【键】方向 / 地面黄点方向 / 实际可走方向"；不可走时用**四向矩阵**（每方向单按一次，比较 N 变化）拿数据；
- **旧/新构建对比**：同一位置截图对比（修复前 vs 修复后），并逐条给"重复处数=0"的验收。

### A3 结论（根因层面）

- **引导不是单一来源**：顶栏文案表、中央逐格指引、地面路径来自不同生成器，目标可以不一致；
- **状态机缺失**：没有区分"行走/已到达/交互中/对白中"，导致"到位动作句"与"下一步句"同时渲染；
- **调试层无门控**：诊断 HUD 在正常模式未关闭，属于"内部信息泄漏"类 bug（用户可见 = 引导混乱 + 遮挡）；
- **目标链无楼层感知**：上楼后目标未推进到"房间门口"，仍指楼梯，造成循环；
- **空目标未防护**：目标指向未 spawn 的 NPC，玩家永远到不了。

### A4 修复原则（可复用）

1. **单条引导**：同一时刻只保留一条"目标+下一步"行（顶栏只放地点；到位时唯一动作句；交互提示复用同一行）；
2. **单一数据源**：顶栏/中央/地面标记由同一套距离场/路径生成，禁止各自算；
3. **状态互斥**：到位状态只显示"当前该做的动作"（上楼/下楼二选一），行走状态不显示到位句；
4. **调试层门控**：诊断 HUD/日志只在显式调试开关下启用，正常启动必须为 0；
5. **目标链单调 + 楼层感知**：每完成一个阶段目标推进到下一真实可交互节点；
6. **空目标防护**：目标必须对该"实体是否已生成/可交互"做校验，不满足则改指最近可交互点。

### A5 验收指标（写进清单）

- 引导元素清单中**重复项 = 0**（同一按键/目标只在一个层级出现）；
- 到达交互点：顶栏=地点、中央=唯一动作句（截图核对）；
- 对白/过场：顶栏+中央**都隐藏**；
- 目标文本序列**单调**（无 A→B→A 循环）；
- 逐格引导：每按一次 N 减 1（或按应用语义递减），方向与地面标记一致；
- （可选，开发提供）引导"下一步"与真实可行走方向 **violations=0**（白盒补充，不当唯一证据）。

## 案例 B：走路卡顿（BFS 2.09 秒 / 间歇性冻结）

### B1 背景

用户反馈"地图上走路卡顿"。黑盒复现：

- 长按方向 800ms 期间，画面只有 2~4 次更新（≈3~5fps），最长无变化 **269~361ms**；
- 同场景复测**一次流畅、一次冻结**（间歇性）；
- 60ms 轻按有 33%~80% 的键没有产生移动（吞键），加剧"走不动"体验。

### B2 证据方法

- `holdprobe`：按住 800ms、每 ~90ms 抓帧，输出"变化帧数/最长冻结/gap"；每场景**重复 2 次**（抓间歇性）；
- `walkprobe`：逐键抓帧，输出"吞键率/每键是否有变化"；
- **同位置前后对比**：修前/修后同一场景、同一操作、同一间隔，才有可比性；
- 区分"卡顿"与"停走"：先单键试探确认该方向可走，再采样（被墙挡住时画面本来就不变）；
- 记录 err.log（0B 为期望；有警告需解释）与场景号，便于白盒对照。

### B3 结论（根因层面）

白盒（开发补充）定位：引导系统每 10/30 帧对**全图 BFS** 重算路线，且 BFS 每个邻居都调用"障碍判定"——而该判定**每次遍历全部事件对象**。微基准（headless）单次路线计算在复杂场景达 **2,090,491.9µs（≈2.09s）**，其他场景 75ms~430ms。
修复：障碍判定改 O(1) 缓存 + 路线缓存（沿路线只移动游标，不重算 BFS）+ 降低重算周期 + 诊断写盘门控。

> 注意：白盒微基准证明"代码路径耗时"，黑盒帧采样证明"玩家看到的卡顿"——两者都要记录，互不替代。

### B4 修复后量化（黑盒）

| 指标 | 修复前 | 修复后 |
|---|---|---|
| hold 800ms 最长冻结 | 269~361ms | **0ms / 83ms** |
| hold 变化帧 | 2~4 / 10 | **9/9、8/9** |
| 轻按（直段） | 7/15、1/15、2/10 | **7 键=7 格、16 键≈15 格** |
| 场景4 单次路线计算（白盒） | 2,090,491.9µs | **3.5µs**（缓存命中） |

### B5 可复用规则

1. **卡顿要量化**：hold 期间采样"变化帧+最长冻结"，不要只写"感觉卡"；
2. **间歇性必须重复采样**（≥2 次），否则容易误判"已修好/没复现"；
3. **先确认可走再测**（排除停走/被挡/对白）；
4. **修前/修后同位置对比**，并记录构建 hash、场景、操作参数；
5. **性能类修复的验收标准**：冻结 <100ms、变化帧 ≥8/10（可按项目调整，但必须提前写死）；
6. **白盒数据只作补充**：函数耗时 2.09s→3.5µs 很漂亮，但仍需黑盒帧采样证明用户体感改善。

## 案例 C：逐键回放/自动走位不能作为验收手段

### C1 背景

某长链节点（含战斗+多场景）反复卡在导航上。开发提供了两代"回放文件"：一段从入口开始的整段按键记录（1315 键 / 6 个交互标记）、一段从第 1 个交互点开始的中段记录（1122 键）；后又提供"落点对齐表"（248 个"方向+剩余格数"签名 → 前缀按键），用于把任意落点对齐到录制起点。结果全部失败：

- 193 键的入口段回放，按 340ms/键执行只前进了约 12 步（录制节奏是 1 键/步，实机是 1 步/0.9~1.0s）→ **整体位置失配**；
- 整段回放从"基准入口"开始仍失配（实机落点与录制落点不是同一格）；
- 签名表存在**同签名多格**：按"西北 约150步"查表执行前缀，结果把角色**带出了该场景**；
- 后续再录"从真实落点开始"的回放，仍因帧率/长按语义差异（headless 60fps vs 实机 45ms hold/300ms gap）与战斗丢键无法复现；
- 测试侧自研"按画面变化自动选方向"的自动走位，在场景门处被带回上一场景，随后卡在角落（多帧完全一致）。

### C2 证据方法

- 记录回放执行的**逐段结果**：执行键数 / N（剩余格）变化 / 位置截图；发现失配立即停（未执行后续交互，避免错乱状态）；
- 记录**录制参数 vs 实机参数**：按键 hold/gap、录制帧率、起点坐标/视角；
- 用**四向矩阵/N 轨迹**验证"引导方向是否正确"，而不是靠回放是否走通；
- 自动化脚本的输出只作"辅助信息"，**不作为通过证据**（任何结论必须在真实按键下复现）。

### C3 结论（根因层面）

- 回放假设"录制环境与运行环境时序语义一致"——**不成立**（帧率、输入处理、战斗随机、动画时长都会改变按键→步数映射）；
- 回放假设"起点唯一"——**不成立**（玩家实际落点随机/多格同签名）；
- 自动走位假设"画面变化=走对了"——**不成立**（场景门/动画/遮挡都产生变化）；
- 因此：**逐键回放与黑盒自动走位都不能作为验收手段**；只能作为"辅助复现/节省人力"的工具，且必须逐段人工核对。

### C4 可复用规则

1. 验收只认**真实按键 + 真实画面**；回放/脚本输出必须由真实操作复现，否则不能写进结论；
2. 如果确实需要回放辅助：录制与回放必须**同环境同时序**（同帧率、同 hold/gap 语义），并在**每个分段加位置/状态检查点**，任何检查点不符立即停止（不得"硬放到尾"）；
3. 长路导航优先"**单键跟提示 + 每 N 步截图核对 N/方向**"；N 不降或方向翻转时按"四向矩阵/停手"处理；
4. 落点/签名对齐表这类"离线映射"必须**唯一键**（含坐标/朝向）且验证过；同签名多格不可用；
5. 自动化工具（含 AI 自研脚本）只能"辅助走位/辅助取证"，**不得进入验收结论**；发现它"看起来能走通"时，反而要警惕场景门/动画误导。

## 三案例的共同结论（写进测试手册）

| 共同点 | 规则 |
|---|---|
| 用户能看到的问题 = 多系统不一致 | 用"同帧多源对照"找矛盾（引导/卡顿/输入都适用） |
| "看起来通过"最危险 | 以真实输入+真实画面复现为准；工具/回放/白盒数据只作辅助 |
| 间歇性/位置相关的问题 | 必须重复采样 + 记录场景/位置/构建；一次不复现 ≠ 修好 |
| 验收要可复核 | 每个结论：现象、证据编号、复现步骤、量化数字、构建 hash |
| 修完要回归 | 同一卡点在新构建复测通过，并抽验相邻功能无回退 |
