# 进度优先与单次判定（v3.3.3）

> 版本：**v3.3.3**｜状态：**验收纪律（写死）**｜适用：Lead / 开发 / 测试 / 记录全员
> 关联：`references/testing/human-ai-dual-progress.md`、`references/standards/slot-safety.md`（**槽安全铁律**：用户槽不可变/自动化只写团队槽/输入前置门禁）、`templates/anchor-ledger.md`、`references/standards/anchors-and-saves.md`、`references/testing/efficiency.md`、`references/standards/no-cheat.md`
> 一句话：**发现 bug 先存进度（团队写进度二）再报；判定 PASS 即通过、不复测（用户 PASS 直接记录）；进度一用户专用、进度二团队专用。**

## 0. 四条规则（总览）

| # | 规则 | 要点 |
|---|---|---|
| 1 | **发现 bug 先保存进度** | 测试遇 bug/卡点，**先在团队进度（进度二）保存当前状态**，记录位置/状态/构建，再报 bug；下次从该进度继续，**不从头重走** |
| 2 | **单次判定即通过（不复测）** | 节点判定 **PASS 后不再复测**（测试/开发同）；**用户测过的节点团队直接记录 PASS、不复测**；仅**用户新报该节点 bug** 或**该节点代码变更**才重开 |
| 3 | **双进度分工** | **进度一=用户专用**（用户测试+保存；团队只读，**不写**）；**进度二=团队专用**（团队测试/续测保存，可覆盖）；其余槽=固定锚点（可选、只读） |
| 4 | **进度槽 ≠ 固定锚点** | 进度槽=当前续测点（用户一/团队二）；固定锚点=稳定起点（只读、不覆盖）；报告/交接写清两者 |

> 双进度完整流程（用户 PASS 记录、团队进度交用户复测、双进度对齐、下一轮）见 `references/testing/human-ai-dual-progress.md`。

## 1. 规则一：发现 bug 先保存进度（再报）

1. **停手**（困难即停）——不盲试、不重启丢现场；
2. **保存团队进度二**（唯一团队续测点）：当前场景/位置/阶段状态；
3. **记录字段**：`进度二槽 / 构建 hash / scene / pos / 中央提示 / 用户已 PASS / 团队已 PASS / 当前节点 / 未完成 / 时间`；
4. **再上报 bug**（现象/位置/复现步骤/期望 vs 实际/证据/建议 + 进度二）；
5. 开发修复后，测试**从进度二继续**（不从头），复测受影响节点。

**禁止（槽安全铁律 v3.3.3）**：团队为存进度**写/覆盖进度一**（任何情况不写用户槽）；**自动化只写团队槽（进度二）**；**注入按键前确认 UI=游戏世界**（菜单/存档/对话框/战斗/过场禁止盲按）；不写游戏数据文件、不用传送/改状态存"进度"。

## 2. 规则二：单次判定即通过（用户 PASS 直接记录）

- 节点经测试自判 PASS（+开发复核/Lead 宣布）后**即通过**，不再因新构建/再确认重复验收；
- **用户测过的节点**：用户明确告知通过（原话/位置/证据）→ 团队**直接记录 PASS（用户验收）**，**不复测**；团队从用户进度一位置继续（只读载入→另存进度二）；
- **重开条件（仅两种）**：①用户新报该节点 bug；②该节点代码变更；
- 其他情况（构建变化但该节点代码未变）→ 不重测已 PASS；只对受影响/相邻节点定向回归。

**反例**：每个新构建全节点重跑；用户已 PASS 又复测；PASS 后长期挂"待复测"；开发改已 PASS 节点不声明。

## 3. 规则三：双进度槽位 + 用户槽保护

| 槽位 | 归属 | 写入权 | 读取权 | 说明 |
|---|---|---|---|---|
| **进度一** | 用户 | **仅用户** | 团队只读 | **团队绝不写进度一**；用户进度是权威起点 |
| **进度二** | 团队 | **仅团队** | 用户可只读 | 团队"当前续测点"；**可覆盖**；记录在案 |
| 其余槽（3/4/5） | 固定锚点（可选） | 团队（建后只读） | 只读 | 节点稳定起点；只读不覆盖 |

**硬性要求**：
1. 团队续测一律**写进度二**；从进度一接续时**只读载入→另存进度二**；
2. **用户槽只读不写**：团队不得保存/覆盖/清空进度一；
3. 双进度**分开登记**（`templates/anchor-ledger.md` §2/§3）；
4. 用户复测通过后：团队把**进度二**同步到通过点；**进度一由用户保存**（团队不代写）。

## 4. 进度槽 vs 固定锚点（必须区分）

| 维度 | **双进度槽（进度一/二）** | **固定锚点** |
|---|---|---|
| 用途 | 进度一=用户进度；进度二=团队当前续测点 | 稳定节点起点（读档直达） |
| 写入 | 一：用户；二：团队（覆盖更新） | 团队建立后**只读、不覆盖** |
| 登记 | `anchor-ledger.md` §2/§3 | `anchor-ledger.md` §1 |
| 交接字段 | 槽位+场景/坐标/中央提示/构建/PASS/未完成 | 锚点 ID+场景/坐标+用途 |

## 5. 报告 / 交接字段（写死 5 项，双进度）

```text
【用户进度状态】<进度一：场景/楼层/坐标/中央提示/构建/时间>
【团队进度状态】<进度二：场景/楼层/坐标/中央提示/构建/时间>
【用户已 PASS 节点】<用户确认通过、团队直接记录的节点（不复测）>
【团队待用户复测节点】<团队进度中等待用户复测的节点（含进度二位置）>
【下一步】<从哪个进度继续；或等用户复测/决定>
```

## 6. 反例合集

| 错误做法 | 后果 | 正确做法 |
|---|---|---|
| bug 后不存进度，从头重跑 | 浪费 20+ 分钟，可能不复现 | 先存进度二再报 bug |
| 团队写/覆盖进度一 | 用户进度受损 | 只读进度一→另存进度二 |
| 用户已 PASS 团队又复测 | 重复劳动/交付慢 | 直接记录 PASS，不复测 |
| 每个新构建全节点重测 | 交付慢、掩盖新问题 | 仅重开"用户新报 bug/代码变更"节点 |
| 团队进度不交用户复测 | 用户不知从哪测 | 写清进度二位置+待复测节点 |
| 用户通过后双进度不对齐 | 下轮从头 | 进度二同步通过点、用户保存进度一 |
| 把进度槽登进锚点表 | 交接混乱 | 双进度/锚点分开登记 |

## 7. 与其他规则的关系

- **双进度**：见 `references/testing/human-ai-dual-progress.md`（规则/流程/反例/槽保护/报告字段）；
- **no-cheat**：进度来自真实操作/合法存档；团队不写用户进度、不伪造进度；禁传送/跳步/自动置 stage；
- **困难即停**：停手后第一件事=保存进度二，再整理问题+建议；
- **经验库**：双进度/锚点用法写入 S*（注明适用条件）；
- **验证自动化**：`anchor_check` 校验固定锚点；进度槽不参与自动断言。

## 8. 每轮检查清单

**开轮**：读用户进度一（只读）→另存进度二；核对用户 PASS 清单；固定锚点校验；构建记录。
**遇 bug**：停手→保存进度二→记录→报 bug。
**PASS 后**：标记 PASS；用户 PASS 直接记录、不复测；仅重开条件才重开。
**收尾/交接**：写 5 项字段（用户进度/团队进度/用户 PASS/待用户复测/下一步）；用户槽未读写声明。

## 9. FAQ

**Q：团队能读进度一吗？** 能，只读；续测必须另存进度二。
**Q：用户已 PASS 的节点还要团队验证吗？** 不用——直接记录 PASS；仅用户新报 bug/代码变更重开。
**Q：团队跑完的进度怎么让用户复测？** 交接进度二位置+待复测节点；用户可只读载入进度二或从进度一走到该点。
**Q：用户通过后进度一谁保存？** 用户保存；团队只把进度二同步到通过点（不代写进度一）。
**Q：固定锚点还需要吗？** 可选；用于节点稳定起点，与双进度分开登记（只读不覆盖）。
