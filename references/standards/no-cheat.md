# 标准 · 禁作弊红线与去作弊审计

> 适用范围：所有角色、所有轮次。违规 = 该轮证据/结论作废、节点重开、上报用户。
> 相关：`SKILL.md` §5、`references/roles/developer.md`、`references/roles/tester.md`。

## 1. 红线（写死）

**禁止任何"让节点看起来通过"的手段**：

| 类别 | 禁止示例 |
|---|---|
| 跳过内容 | 连按空格跳过剧情/战斗；跳过入场脚本/onEnter；跳过教学/演出 |
| 自动判定 | 自动胜利（`auto_win`/`force_win`/`_no_battle`）；自动置 stage/flag/任务完成；自动给道具/经验 |
| 位置作弊 | 传送/跳场景（`debug_jump`/`teleport`）；瞬移到目标；伪造出生点 |
| 判定放宽 | 宽区域/伪交互（任意位置 SPACE 推进剧情）；放大触发半径；改验收标准；改数据让条件恒真 |
| 测试适配 | **为测试/自动化改游戏代码**：合成触发（如合成上下楼）、强制落点/坐标校正、任意位置 SPACE、test-only 分支/埋点后门、stub/假事件（详见 §6 架构铁律） |
| 证据作弊 | 调试键/`--debug-hud`/`--auto` 画面充当验收证据；伪造截图/日志/存档；改报告结论 |
| 存档作弊 | 覆盖锚点；用合成存档宣称正常流程通过（合成必须标注并单独定性） |

**必须**：真实键鼠输入、真实战斗/对白逐页、正常启动（无调试参数）验收；用户批准的取舍（如难度设计变更）必须标注"用户批准"，否则结论作废。

## 2. 主线问题先停手（防"通过式绕行"）

- 收到问题先判**主线相关**：影响剧情推进、场景切换/门、关卡通路、关键战斗"能打且能过"、节点验收目标/锚点 = 主线相关。
- 主线相关 → **立即停止操作**（停改码、停跑、停止一切"让它通过"的尝试），整理现象+证据+根因初判+候选方案（≥2，利弊）→ 上报 Lead → 用户决策；**批准前不得实施任何绕行/取舍**。
- 非主线 → 普通修复流程；仍不得用上述红线手段。

## 3. 去作弊审计清单（每轮结束/发版前）

### 3.1 代码扫描（grep 关键词）

```text
auto_win / force_win / _no_battle / skip_dialog / skip_battle / skip_story
teleport / debug_jump / jump_scene / goto_scene / set_stage / set_flag / auto_mode
no_collision / no_clip / god_mode / cheat / debug_cheat / force_pass
```

要求：命中项**逐条分类**为「注释/文档说明」「debug 探针（仅 `--debug-hud`/`--auto` 生效）」「正常机制（如存档/门脚本 onTeleport）」「❌ 作弊代码」；作弊代码必须删除或降级为 debug 门控。

### 3.2 正常启动验证

- 用**正常启动**（无 `--debug-hud`/`--auto`/调试键）跑一遍：**0 条调试输出**（headless/normal 模式日志应为空或仅正常打印）；
- 调试浮层/固定 HUD/边缘诊断面板在正常模式**不得出现**（可在截图验收项中列"无调试浮层"）；
- 关键流程回归 fails=0（P0/主链/前序节点/读档/fade 等）。

### 3.3 证据侧验证

- 战斗证据须能看出**真实回合/真实伤害/真实结算**（不是一击必杀/跳过动画）；
- 剧情/对白证据须**逐页**（可数页数），不得只截一页；
- 存档/锚点未被覆盖（读档次数、存档操作记录为 0）；
- 作弊清理后需重新复测节点（旧通过作废）。

## 4. 清理记录模板（写进项目台账/DEV_REPORT）

```text
### 去作弊清理 · <构建/日期>
- 扫描关键词：<...>
- 命中与处置：
  | 位置（文件:行） | 命中 | 分类（注释/debug/正常/❌） | 处置 |
- 正常启动验证：<命令/结果：0 调试输出 / 无浮层>
- 回归：<项 → fails=0>
- 结论：<无作弊残留 / 残留项与风险>
```

## 5. 违规处理

1. 发现作弊取证/跳过手段：**该轮作废**，节点重开；
2. 开发/测试回执如实说明（谁、哪一步、为什么）；
3. Lead 向用户报告；必要时调整流程（如禁调试键进入测试环境、截图/日志集中校验）；
4. 用户批准的取舍（非原版设计）单独标注并进入验收报告"用户批准"节。

## 6. 架构铁律：禁止测试后门 / 禁止为测试改游戏（v3.2.1，用户拍板）

**铁律（写死）**：**游戏代码不得为测试/自动化添加任何逻辑**；自动化只能**外部输入（真实按键）+ 外部观测（截图/状态导出）**，不得依赖游戏内测试钩子/后门。

### 6.1 禁止清单

- 为测试/自动化在**游戏代码**中添加：合成触发（如合成上下楼/合成本该由事件触发的门/对话）、强制落点/坐标校正、任意位置 SPACE / 宽区域交互、test-only 分支（`if test`/`test_only`/测试埋点后门）、stub/假事件；
- 以"让 walker/自动断言通过"为由改落点/触发/引导/验收标准，或改数据让条件恒真；
- **测试加速（test-fast）/失败快照等**：必须做**构建外工具**或**独立 debug 构建**；默认**不进入正式包**；正式包不得含测试分支/后门/时间缩放开关。

### 6.2 真实案例（round78：用户明确否决，已回退）

- 曾为自动走位/复验方便加：**任意位置 SPACE**（A14 等）、**合成上下楼触发/落点校正**（如 1F base 合成上楼脚本）→ 用户否决：属测试适配/overfit，要求回退；
- 已回退（证据：`_playtest_regress_dev/DEV_REPORT_cheat_cleanup.md` §九十三~§九十五、`_playtest_regress/bug-ledger.md` R77-EXIT-6 / R78-STREET-5）：
  - 取消 A14「任意位置 SPACE」→ 必须走到**店门（半径 140）按空格执行真实脚本 1649**；
  - 取消剧情后**强制落点校正** → 恢复真实落点/真实门；上下楼走真实事件/真实脚本。
- **结论**：测试效率问题用**锚点/外部脚本**解决，不得向游戏代码里加钩子。

### 6.3 允许 vs 不允许

| 允许（构建外/外部） | 不允许（游戏代码内） |
|---|---|
| 锚点库（合法存档读档）、真实按键注入、截图/状态导出、任务树节点核对、失败快照、run_verify 打包 | 合成触发、强制落点、任意位置 SPACE、测试专用分支/钩子、为测试改数据/改验收标准 |
| 独立 debug 构建里的 test-fast（**仅时间缩放**，不改逻辑、不跳剧情/战斗、不改状态） | 正式包带 test-fast 分支、测试后门或任何"测试模式"逻辑 |

### 6.4 正确做法

发现真实问题 → 修**游戏性真实问题**（数据/碰撞/事件/脚本/引导），或按流程调整验收口径（Lead + 用户批准并记录）；测试效率问题 → 锚点库/外部工具/分层测试；**不得"让测试绕过去"**。

### 6.5 审计与处理

- 发版前 grep 关键词（`test_`/`_test`/`test_only`/`test_hook`/`test_fast`/`if.*test`/`synthetic`/`force_pos`/`force_*`/`auto_win`/`debug_jump`/`任意.*SPACE` 等），并**对比正式包/正常启动行为**（无测试分支/无调试浮层/无额外输出）；
- 发现后门或"为测试改游戏"：**该轮证据作废、回退改动、节点重开、上报用户**；开发/Lead 记录决策与回退 commit；
- 与 §1 关系：§1 管"测试/验收过程禁作弊"，本节管"**游戏代码不得因测试而改**"；两者叠加——任何"让测试好过"的改动都不得进入游戏代码。
