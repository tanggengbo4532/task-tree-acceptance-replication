# Acceptance integrity

Acceptance evidence must show the actual user-facing task under ordinary input and a normal launch.

## Invalid methods

Disallow direct state, database, memory, or save edits to produce success. Disallow teleports, forced victories, skipped initialization or dialogue, synthetic triggers, enlarged interaction regions that bypass the intended action, weakened checks, fabricated screenshots, and treating debug captures as normal-use evidence.

Keep diagnostic tools on the Developer side. Production packages must exclude test-only branches and backdoors. Any optional time-only acceleration uses a separate test build or an external harness. Label its evidence and preserve logic, outcomes, and required transitions.

## Main-route decisions

If a proposal changes main-route meaning, difficulty, triggers, or the acceptance objective, stop and send the Lead the symptom, evidence, and options with trade-offs. Record the user's decision before applying the change, and verify the implemented behavior through ordinary use.

## Audit each round

- Inspect relevant changes for forced state changes, debug gates, skipped events, and revised triggers. Check normal startup and the affected behavior.
- Compare the real input log, screenshots, evidence manifest, build, and attempt. Check that the user could perform the observed sequence and that the evidence supports the claimed result.
- If a shortcut invalidates a claim, preserve the record, mark the verdict invalid, inform the Lead, and apply the node-specific reopen rule where relevant. Use fresh evidence from the corrected build.
- Archive the finding, affected node and build, evidence, removal commit, and corrected verification. Report uncovered areas plainly.
