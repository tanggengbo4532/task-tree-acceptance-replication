# 标准 · 锚点与存档纪律

> 目标：节点可**断点续测**、已通过部分不重测，同时**不污染用户存档**、不把"读档状态"当成"全新流程"。
> 相关：`SKILL.md` §2、`templates/anchor-ledger.md`、`references/roles/tester.md`。

## 1. 什么是锚点

**锚点 = 到达某节点起点时的一致的可恢复状态**，形态随应用形态不同：

| 形态 | 锚点形态 | 恢复方式 |
|---|---|---|
| 桌面游戏/应用 | 游戏内存档槽/快照文件/账号状态 | 启动后读档/载入快照 |
| Web 应用 | 账号 + LocalStorage/DB 快照 | 登录 + 恢复数据 |
| CLI/服务 | 数据目录快照/DB dump | 还原目录/导入 dump |
| 关卡类 | 指定关卡+角色状态+关键 flag | 关卡选择/调试入口（须为正常入口） |

## 2. 纪律（写死）

1. **锚点只读**：测试只**载入**锚点，不覆盖、不删除、不新建同槽位；如需建新锚点必须 Lead 批准并在台账标注。
2. **读档次数记录**：每轮报告写"读档 N 次（哪个槽）"；除必要载入外**全程不存档**。
3. **锚点必须先验证**：新锚点建立后，先验证"载入即可复现该节点起点"（场景/坐标/关键状态/UI），再写入任务树。
4. **合成状态单独定性**：脚本/编辑器/调试造的存档必须标注"合成"，结论不能与正常流程通过等同。
5. **版本兼容**：构建改动可能使旧档不兼容（场景号/字段变化）→ 记录"旧档不可用/需迁移"，不要让测试用旧档强行测新流程。
6. **锚点缺失不跳步**：节点过粗导致没有可用锚点 → 开发拆分/补锚点后再测，不能"从头重跑一切"当作进度。

## 3. 锚点台账（每项目一份，模板 `templates/anchor-ledger.md`）

最小字段：

```text
| 锚点 ID | 槽位/路径 | 场景/关卡 | 关键状态（坐标/等级/道具/flag） | 建立时间 | 建立构建 | 只读 | 上次验证 |
| A-SLOT1 | 存档槽一 | 场景2 客栈房间 | pos(1248,296) 07:52 | ... | <hash> | 是 | <轮次> |
```

**核对项**：每轮开始读档后，核对顶栏/场景/坐标/关键数值是否与台账一致；不一致=锚点漂移，停下来报告（可能被覆盖/版本不兼容）。

## 4. 存档兼容与回滚

- 改场景表/存档字段/地图数据时，开发必须在回执里写"存档兼容性"（旧档可用/需迁移/不可用）；
- 旧档不可用时：保留旧锚点文件（只增），新构建重建锚点并写台账；
- 禁止为了"让测试快速到节点"而用调试跳转/传送——这属于作弊（见 `no-cheat.md`），只能用正常读档/正常流程。

## 5. 回执要求

测试报告与记录归档必须含：
- 本轮读档：**槽位 + 次数**；是否存档（应为 0）；
- 锚点是否与台账一致；是否发现漂移；
- 五锚点/全部锚点"未被覆盖"的声明（recorder 审核项）。
